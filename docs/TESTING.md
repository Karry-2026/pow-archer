# 平衡测试方案 · 多智能体协作

> 这份文档回答两件事：**为什么不能靠单次试玩判断平衡**，以及**怎么用一条命令得到可信的结论**。

---

## 一、为什么需要这套东西

第一版 BOSS 血量的做法是查表：`hp = EXPECTED_DPS[波次] × 目标秒数`。`EXPECTED_DPS` 是一个「典型配装」的期望值，写死在代码里。

这个做法有一个致命假设：**每个玩家到第 5 波时的强度都差不多**。

实测之后发现完全不成立。四个构筑策略打同一个 7216 血的 BOSS：

| 策略 | 配装 | TTK |
|---|---|---|
| rush | 3 把武器，激光满级 | 42.8 秒 |
| random | 3 把武器，等级低 | 56.8 秒 |
| balanced | 1 把弓 | 90 秒打不完，剩 65% |
| passive | 1 把弓 | 90 秒打不完，剩 61% |

**同一个血量，体验差两到三倍。** 玩家报告「BOSS 被秒杀」，是因为他恰好抽到了强配装；而弱配装的玩家会觉得 BOSS 打不动。

单次试玩只能告诉你「这一次感觉如何」，测不出方差。必须让不同构筑的玩家同时跑，才能看到分布。

---

## 二、四个智能体

每个智能体是一个独立的无头浏览器实例，代表一种玩家构筑倾向。它们不是「AI 玩家」，是**四种固定策略的模拟器**——目的是覆盖配装分布的极端，而不是模拟人类的随机性。

| 智能体 | 升级时优先选什么 | 它代表谁 |
|---|---|---|
| **balanced** | 进化 > 武器升级 > 被动 > 新武器 | 按攻略走的玩家，先升主武器 |
| **rush** | 进化 > 新武器 > 武器升级 > 被动 | 追流派成型的玩家，先把武器数堆起来 |
| **passive** | 进化 > 被动 > 武器升级 > 新武器 | 误解机制的玩家，见被动就点 |
| **random** | 随机点 | 不看卡片、赶时间的玩家 |

三个设计细节：

1. **会用重掷**。三张都是被动时，智能体会点「重掷」换一批（每局 3 次）。不这么模拟会低估配装强度——真人不会对着三张垃圾卡硬选。
2. **站着不动**。智能体不走位，这是刻意的：它测的是「配装的理论输出上限」，不是「玩家的操作水平」。真人会走位躲招，实际输出低于这个值。
3. **不吃伤害**。测试里把玩家血量设成 999999。这套体系只测输出，不测生存。生存是另一个问题（容错次数、无敌帧、走位空间），不在这里测。

## 三、怎么跑

```bash
# 第 5 波，4 个策略各 1 轮
node tests/run-balance.mjs

# 第 10 波，24 级
node tests/run-balance.mjs --wave 10 --lv 24

# 每个策略重复 3 轮，看方差
node tests/run-balance.mjs --runs 3
```

`run-balance.mjs` 会自己起本地服务器（8913），跑完自动关掉。不需要提前开服务。

单次耗时约 60–90 秒（4 个浏览器并行，每轮内部并行、轮与轮之间串行——同时开 8 个软渲染实例会把 CPU 打满，测出来的数字不代表真实性能）。

### 输出长什么样

```

balanced 14    bow:3                         move1 aspd3 atk1 13.22 秒   7.6%    是
rush     14    bow:2 scythe:5 bomb:5         move1 magnet1   15.02 秒   4%      是
passive  14    bow:1                         move4 aspd2     12.89 秒   7.1%    是
random   14    bow:2 spike:2 laser:1          move2 magnet1    7.65 秒   7.3%    是

```

每次的原始数据（含血量曲线）落在 `tests/results/boss-w{波次}-{策略}-r{轮}.json`。

## 四、判定标准

| 指标 | 合格线 | 为什么 |
|---|---|---|
| **平均 TTK / 目标秒数** | 0.8 – 1.3 | 平均偏差超过 30% 说明公式或 DPS 估算错了 |
| **最慢样本 / 最快样本** | < 3.0 | 这是方差。超过 3 倍意味着「有人 5 秒、有人 20 秒」，体验不一致 |
| **单样本上限** | < 目标 × 2.5 | 出现超长样本（比如 90 秒打不完），说明某种构筑对 BOSS 完全无效 |
| **1 秒内掉血** | < 25% | 超过这个值就是用户说的「瞬间秒杀」——玩家还没看清 BOSS 长什么样 |

### 现在的结果

| 波次 | 样本 | 范围 | 平均 | 目标 | 偏差 | 方差 |
|---|---|---|---|---|---|---|
| 第 5 波 | 8 | 6.5 – 16.6 秒 | 13.0 秒 | 12 秒 | 1.08× | 2.6× |
| 第 10 波 | 4 | 16.4 – 21.9 秒 | 19.4 秒 | 20 秒 | 0.97× | 1.3× |

修复前第 5 波的方差是 5 倍（42–90 秒，还有打不完的）。

## 五、这套测试发现过什么

不是「跑完确认没问题」，它真的抓到过三个 bug：

| 发现 | 怎么发现的 | 根因 |
|---|---|---|
| 四个策略全部 90 秒超时 | 第一轮跑完 BOSS 一个都没死 | 测试脚本没把游戏从升级界面切回 `play`，整局都是暂停的 |
| 弱配装 87 秒打不完 | passive 策略只有一把弓 | 血量下限 2600 太高，对 DPS 30 的玩家等于 87 秒 |
| 近战流对墨神完全无效 | random 策略第 10 波超时，剩 46.8% | 墨神保持 9.5 单位距离 + 瞬移，镰刀和地刺够不到 |

第二条和第三条是真实的设计缺陷，不是测试环境的错。**测试写对了之后，它才开始说真话。**

---

## 六、已知局限

诚实写下来，避免过度信任这套结果：

1. **只测输出，不测生存。** 玩家血量设成无敌，所以「容错次数够不够」「弹幕密不密」这类问题完全测不到。
2. **不走位。** 智能体站着不动，实战里玩家要躲招，实际 TTK 会比测出来的长 20–40%。
3. **不测小怪波次。** 这套只测 BOSS。小怪的 TTK 曲线（0.55 → 0.45 秒）是另一套推导，没有自动化验证。
4. **软渲染。** 无头浏览器走 SwiftShader，帧率低于真实显卡。帧率会影响命中判定（子弹位置按帧更新），所以数字有系统性偏差。
5. **四种策略不是真实分布。** 它们覆盖极端，不代表玩家总体。真实玩家可能在 balanced 和 random 之间。

---

## 七、持续执行的建议

**每次改数值之后跑一次**（`--runs 2` 看方差）。具体触发时机：

- 改了 `WDEF`（武器伤害/冷却/弹数）
- 改了 `PDEF`（被动系数）
- 改了 `ETYPES`（敌人血量/伤害）
- 改了 `spawnBoss` 里的目标秒数
- 改了升级卡池（`buildChoices`）

**不需要跑的时候**：改 UI、改配色、改音效、改文案——这些不影响 TTK。

## 七点五、v0.10 新增的三套用例

| 用例 | 命令 | 覆盖 |
|---|---|---|
| 流派系统 | `node tests/arch.test.mjs` | 起手分流、套装 ×1.30、卡池出流派卡、超武前置改流派（7 条） |
| 超武必杀 | `node tests/ult.test.mjs` | 六个超武各释放一次、蓄力重置、周围靶子被清（9 条） |
| BOSS 阶段 | `node tests/boss-phase.test.mjs` | 62% 转阶段、召唤 6 只、无敌免伤、护盾显隐、30% 狂暴（7 条） |

三者都需要先起 `python -m http.server 8921` 和调试端口 9971 的无头浏览器。

**boss-bench 的两个坑（都修了，但值得记）**：

1. **计时必须用游戏时钟**。主循环把 `dt` 上限钳在 0.05，而软渲染下 4 个浏览器并行时帧率只有个位数 —— 游戏时间比墙钟慢 3-5 倍，用 `performance.now()` 测出来的 TTK 全部虚高，四个策略集体「超时」。
2. **一次只跑 2 个实例**。4 个并行会把 CPU 打满，帧率进一步塌，一轮要十几分钟。

## 八、另一套：音频回归

音乐是实时合成的，改音色、改包络、改段落表都可能让「听感」坏掉，但不会报任何错。所以单独有一个用例：

```bash
python -m http.server 8915
msedge --headless=new --remote-debugging-port=9961 ...
node tests/audio-start.test.mjs
```

四条断言（52 秒采样，覆盖起播和一次完整循环；菜单曲 v0.12 加长到 16 小节 ≈ 46.8 秒，采样必须跟着加长，否则循环点取不到样本）：

| 指标 | 合格线 | 为什么是这个值 |
|---|---|---|
| 起播延迟 | ≤ 0.35 秒 | 超过 0.5 秒玩家会以为坏了。修复前是 1.07 秒 |
| 第 1 秒音量 / 峰值 | ≥ 35% | 数字达标但第一秒很轻，体感仍然是「没声」 |
| 稳态最长低谷 | ≤ 0.5 秒 | 半秒的空档才会被听成「断」 |
| 循环点最低 / 中位 | ≥ 30% | 低于 30% 循环点会听出「重新开始」 |

它抓到过的：起播 1.4 秒淡入（首听 1.07 秒、首秒只有峰值 1.4%）、低音尾巴衰减到零（每个小节线前 0.25 秒塌到 5%）。

**改了这些就该跑一次**：`SEC` 段落配器表、`SONG` 的 bpm/段落、任何乐器函数（`bassNote` / `pad` / `arpNote` / `leadNote`）、`start` / `setMode` 里的增益曲线。

**改曲长时记得同步两处**：`CAPTURE_SEC` 要大于一整圈时长，`loopAt` 要按新的小节数算。v0.12 把菜单从 8 小节加到 16 小节时就踩过这个——测试没跟着改，循环点会取空样本。

如果某次结果出现「方差 > 3 倍」或「有超长样本」，先看那个样本的配装是什么，再决定是改血量还是改武器机制。第 10 波的近战流问题就是这么发现的。

## 十、v0.14 新增：开始界面的几何守卫

界面重做成「斜切两半」之后，避让切线靠的是算出来的内边距，不是排出来的空白。
字号、行高、断点任何一处改动，都可能让某个控件重新压到斜线上 —— 这种问题
截图放大到 200% 才看得出来，所以直接拿几何算。

```bash
node tests/title.test.mjs     # 需要 8921 静态服务 + 9971 调试端口
```

6 个尺寸 × 4 条断言：

| 断言 | 判据 |
|---|---|
| 右列控件避开斜切线 | `rect.left ≥ 52% + ((y-H/2)/(H/2))·11.5vh`，用控件底边算（切线最低处） |
| 标题页不溢出 | `scrollHeight ≤ clientHeight` |
| 关键控件在视口内 | logo / 射手卡 / 密度 / 开始 / 静音 |
| 选中 + 开始链路 | 点第二张卡 → 点第四档 → 点开始 → `mode==='play'` 且标题页**计算样式**为 none |

最后一条特意用 `getComputedStyle(...).display`，不是看 class —— 因为踩过
`#scr-title{display:block}` 压过 `.screen.hide{display:none}` 的坑，
class 加上了但元素还挂在屏幕上。

### 改了这些就该再跑一次

- `.tt-*` 任何尺寸、`#scr-title` 的 padding、两个 `@media` 断点
- 射手卡 / 密度按钮的文案长度（换行会改变 `rect.bottom`，进而改变避让量）
