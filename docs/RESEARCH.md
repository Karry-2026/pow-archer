## 三、参考游戏机制拆解

### 《弓箭手大作战》（Arrow.io 类）

核心逻辑：控制角色移动，自动朝最近目标射击，不需要手动瞄准。所有操作围绕走位。

升级时从随机技能里三选一，技能分四类：武器种类、武器效果、属性加成、特殊技能。

武器梯队（来自攻略资料）：

| 武器 | 特点 |
|---|---|
| 激光 | 攻击强，弹道穿墙 |
| 地刺 | 走过留下持续伤害区域，穿墙 |
| 炸弹 | 范围伤害，需要堆雷数和体积 |
| 近战（镰刀、太刀） | 穿墙，近身爆发高 |
| 弓箭 | 初始武器，属性平庸 |

武器效果类技能：弯曲弹道、折线弹道、左右射击、后射击、连射、环绕。

这套设计的价值：**武器是变量，属性是常量**。玩家每次升级改变的是玩法，不是数字。

### 《吸血鬼幸存者》

核心循环：怪物从四周持续涌来 → 击杀掉经验宝石 → 拾取升级 → 三选一 → 撑过时间。

三个关键机制：

1. **经验宝石驱动成长**。成长节奏由拾取驱动而不是击杀驱动，玩家会主动往怪多的地方走。这是「主动迎战」而不是「被动躲」的设计。
2. **超武进化**：特定武器满级 + 对应被动满级 + 开黄金宝箱 = 合成超武，获得更强的范围伤害和特殊效果。
3. **Limit Break**：所有武器和被动满级后，不再给金币或鸡腿这类垃圾选项，转为给某个武器的某项属性无限升级。

第 3 条直接对应我们「后期全是加血」的问题。

另外两个隐性设计（来自认知偏差分析文章）：

- 升级时给已有武器隐藏的概率加成，避免玩家因为找不到想要的道具而沮丧。
- 每局前 6 个宝箱是预设的，第 6 个必出三级宝箱，让玩家早期就体验到「抽到好东西」。

## 四、数值设计引用

### TTK 标准

| 类型 | 目标击杀耗时 |
|---|---|
| PvE 杂兵 | 2-5 秒 |
| PvE 精英 | 15-30 秒 |
| PvE BOSS | 2-5 分钟 |

有效 DPS 公式：`base_damage × attack_speed × crit_chance × crit_multiplier × (1 - target_mitigation)`

原则：TTK 定义游戏节奏。太短就没有决策空间，太长就变成枯燥。平衡先算清楚公式，手感作为最后的校验，不能只靠感觉调。

### 曲线形状选择

| 曲线 | 特性 | 适用 |
|---|---|---|
| 线性 | 可预测，长期无聊 | 新手引导节奏 |
| 指数 | 早期刺激，后期碾压 | 短局 roguelike 的敌人成长 |
| 对数 | 早期慷慨，后期边际递减 | 玩家力量，防止失控 |
| S 曲线 | 慢起、中段陡、后期平台 | 整体战役推进 |

### 锯齿（sawtooth）难度模型

每个章节的节奏：

1. 开始略低于玩家强度，给呼吸空间
2. 段中爬升，追平玩家强度
3. BOSS 或高潮超出玩家 10-20%，形成挑战尖峰
4. 下一章回落，重新从低于玩家强度起步

「玩家力量」和「敌人难度」是两条独立曲线，中间的差就是挑战感。两条都平了，游戏就死了。

### 线性递增 + 阶梯跳跃

来自塔防游戏数值实践：

- 血量每波 +5%（线性）
- 每 5 波额外 +10%（阶梯）

效果：不会出现「第三波突然打不动」，也不会出现「数值一路平推到结束」。

反面案例：每波直接 +20% 血量，玩家在第三波就会卡住。

### 曲线错配的经典错误

敌人血量按区域指数增长（每区域 2 倍），玩家伤害按等级线性增长（每级 10%）。到第 5 个区域，敌人血量是基础的 32 倍，玩家伤害只有 1.5 倍。差距会无限扩大，后期区域直接不可玩。

## 五、引擎对比数据

来源：多份 2026 年的 Web 引擎对比资料。

| 引擎 | 空项目包体 | Web 技术 | 语言 |
|---|---|---|---|
| Godot 4 | Brotli 约 5 MB / gzip 约 9 MB | WebGL2 + Wasm | GDScript（C# 不支持 Web） |
| PlayCanvas | 约 1-2 MB | WebGL2 + WebGPU | JS / TS |
| Babylon.js | 约 1-2 MB | WebGL2 + WebGPU | JS / TS |
| Three.js | 核心约 150 KB | WebGL2 + WebGPU | JS / TS |
| Unity | 空白 WebGL 8-11 MB | WebGL / WebGPU | C# |
| Defold | 约 1.14 MB | WebGL + Wasm | Lua |

Godot Web 导出的额外限制：

- 需要 `Cross-Origin-Opener-Policy: same-origin` 和 `Cross-Origin-Embedder-Policy: require-corp` 两个响应头，否则 SharedArrayBuffer 不可用，引擎启动失败。
- 从 4.3 起可以导单线程版本绕开这个要求，但性能有损失。
- 只支持 Compatibility 渲染器。
- macOS 和 iOS Safari 有上游 bug。

一条来自同类项目的工程记录，关于可移植性：

> 从第一天就按可移植来设计，把模拟核心保持纯逻辑、引擎无关、可完全无头测试。这样将来的移植是「重写渲染层」，不是「重写游戏」。

这条建议直接影响了我们「逻辑与渲染分离」的规划。

## 六、技术参考

### Three.js 版本选择

r150 是最后一个提供 UMD 构建（`build/three.min.js`）的版本之一，r155 之后官方移除。选 r150 是为了能用一个 `<script>` 标签引入，不需要 importmap 和构建步骤。

弃用提示：控制台会警告 `build/three.js` 和 `build/three.min.js` 在 r160 会移除，不影响当前使用。

### 卡通着色与描边

- 卡通着色用 `MeshToonMaterial` + 自定义 gradientMap。默认是平滑的，要换成阶跃贴图才有色块感。
- gradientMap 用 `DataTexture`，单通道 `RedFormat`。注意：宽度不是 4 的倍数时要设 `unpackAlignment = 1`，否则 WebGL2 上传会失败。
- 描边用背面外壳外扩（inverted hull）：同一份几何画第二遍，`BackSide` 材质，放大 1.15-1.3 倍。比后处理边缘检测便宜得多。

### 实例化渲染

`InstancedMesh` 的 `count` 可以动态设置，配合 `instanceMatrix.needsUpdate` 每帧更新。要注意设 `frustumCulled = false`，否则包围盒算错会被错误剔除。
