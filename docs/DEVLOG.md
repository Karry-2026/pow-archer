## 01:02 · 调研参考游戏

### 《弓箭手大作战》（Arrow.io 类）

拆出来的三个可复用机制：

1. **虚拟摇杆走位 + 角色自动朝最近目标射击**。玩家不需要瞄准，所有操作围绕走位。这把复杂度从「手眼协调」转到「决策」，对非核心玩家友好。
2. **升级时从随机技能里三选一**，技能分四类：武器种类、武器效果、属性加成、特殊技能。武器是变量，属性是常量。
3. **武器体系分层**：激光穿墙、地刺留场、炸弹范围、镰刀近战，每把的打法逻辑完全不同。

### 《吸血鬼幸存者》

三个可复用机制：

1. 击杀掉经验宝石 → 拾取 → 升级 → 三选一。成长节奏由拾取驱动，不是由击杀驱动，所以玩家会主动往怪物密集处走。
2. 武器满级 + 对应被动满级 + 黄金宝箱 = 超武进化。这是「后期不无聊」的核心设计。
3. 怪物从四周持续刷新，密度随时间提升，压力来自数量而不是单体强度。

### 融合方案

取弓箭手的「走位 + 自动索敌」降低操作门槛，取幸存者的「经验 → 三选一 → 超武」作为成长曲线，再加用户要求的宝箱和背包。

## 01:06 - 01:15 · 写代码

分成三段写，每段写完做语法检查，避免一次性写两千行出一堆错。

| 段落  | 内容                                                       |
| --- | -------------------------------------------------------- |
| 第一段 | HTML 结构、全部 CSS、渲染器初始化、卡通材质工厂、程序化贴图、场景搭建、相机、屏幕特效、音效合成     |
| 第二段 | 实例池工具、粒子、冲击波、玩家模型、4 种敌人、BOSS、子弹池、经验宝石、宝箱                 |
| 第三段 | 6 把武器定义、被动定义、开火逻辑、升级卡池、宝箱开箱、背包渲染、波次与刷怪、输入处理、HUD、主循环、流程控制 |

几个刻意的技术决定：

**全部用程序化几何**。玩家、敌人、宝箱、围墙没有一个外部模型文件，全部是 `IcosahedronGeometry`、`ConeGeometry`、`TorusGeometry` 现场拼的。原因：评审打开时不会因为资源加载失败看到白屏。

**全部走 InstancedMesh 池**。同屏 170 个敌人、300 发子弹，如果每个都是独立 Mesh 就是 470 个 draw call，核显必卡。用实例化把敌人压到每类 2 个 draw call（本体 + 描边），子弹压到 3 个。

**音效用 Web Audio 现场合成**。射击是方波下滑，命中是噪声爆发，升级是上行琶音，全部由代码生成，不加载任何音频文件。

**卡通着色不用后处理**。通常做描边要接 EffectComposer 做边缘检测，但那要额外加载三个脚本模块。改用背面外壳外扩：同一份几何再画一遍，用 `BackSide` 材质，放大 1.15 倍，形成黑边。成本低，风格更接近手绘。

## 01:42 · 数值改造

### 先诊断

算了下实际的数值，问题很清楚：

| 数值       | 第 1 波 | 第 10 波 | 倍数         |
| -------- | ----- | ------ | ---------- |
| 敌人血量倍率   | 1.00  | 4.06   | 4.1x       |
| 敌人伤害     | 固定    | 固定     | **1.0x**   |
| 玩家可达 DPS | 15    | 500+   | **30x 以上** |

两个致命问题：

1. **敌人伤害完全不成长**。玩家血量上限 240，敌人打 7-16 点，无论打到第几波都是这个数。所以玩家死不了。
2. **环绕镰的 DPS 失控**。冷却写的是 0.05 秒，意思是每秒触发 34 次，每次对范围内所有敌人造成 42% 伤害。算下来单目标每秒 513 点，还是 AOE。比单体的激光还高 2 倍，所有武器在它面前没有存在意义。

### 依据

查到的公开方法论，三条：

1. **TTK（击杀耗时）标准**：普通杂兵 2-5 秒，精英 15-30 秒，BOSS 2-5 分钟。TTK 定游戏节奏，太长变枯燥，太短没决策。
2. **锯齿（sawtooth）难度曲线**：每段起点略低于玩家强度给呼吸空间，段中爬升追平，BOSS 超出 10-20%，下一段回落再起步。难度要有峰谷，不能是一条平滑直线。
3. **线性递增 + 阶梯跳跃**：每波线性小涨，每若干个波次额外跳一档。纯线性会「第三波突然打不动」，纯指数会后期崩塌。

还有一条负面清单：敌人血量指数增长配玩家伤害线性增长，落差会无限扩大。反过来玩家成长远超敌人，就是我们现在的情况。

### 改法

敌人血量放弃线性，改成按波次查表，表本身按锯齿设计：

| 波次 | 血量   | 伤害   | 备注              |
| -- | ---- | ---- | --------------- |
| 1  | 1.00 | 1.00 | 呼吸区             |
| 2  | 1.12 | 1.02 |                 |
| 3  | 1.38 | 1.16 | 台阶：尖刺兽入场        |
| 4  | 1.52 | 1.20 |                 |
| 5  | 1.92 | 1.34 | 尖峰：BOSS         |
| 6  | 1.66 | 1.38 | 回落 13%，台阶：投掷手入场 |
| 7  | 1.86 | 1.44 |                 |
| 8  | 2.32 | 1.58 | 台阶：肥球成群         |
| 9  | 2.68 | 1.72 |                 |
| 10 | 3.35 | 1.92 | 尖峰：最终 BOSS      |

波内再线性加 6%（血量）和 5%（伤害），避免整波一个强度。

三个配套改动：

- **环绕镰冷却 0.05 → 0.50 秒**，单次伤害从 42% 提到 100%。DPS 从 513 降到约 180，仍是强力 AOE，但不再碾压一切。
- **敌人伤害接曲线**，第 10 波是 1.92 倍再加波内递增。玩家 240 血，被碰 5-6 次就得走位。
- **加精英怪**。第 3 波起按概率出现，血量 5.5 倍、伤害 1.55 倍、体型 1.32 倍、经验 6 倍，脚下一圈旋转的黄色光环。这是曲线上的小尖峰，也是宝箱的稳定来源。

## 01:44 · 升级系统重做

用户指出的「后期全加血」，在《吸血鬼幸存者》里的解法叫 Limit Break：所有武器和被动满级后，不再给金币或鸡腿这类垃圾选项，转为给武器叠加无限升级。

照这个思路加了两层：

**超武进化**。武器满 5 级 + 指定被动到 3 级，进化成完全不同的形态：

| 武器   | 需要 | 进化成  | 效果               |
| ---- | -- | ---- | ---------------- |
| 爆裂弓  | 攻速 | 箭雨   | 12 发扇形，全穿透       |
| 穿透激光 | 攻击 | 湮灭射线 | 4 束，持续 1.35 秒    |
| 环绕镰  | 移速 | 血月斩  | 6 刃，范围 +60%，命中回血 |
| 抛掷炸弹 | 暴击 | 陨石雨  | 6 颗，爆炸半径 +50%    |
| 回旋镖  | 磁力 | 无限回旋 | 4 枚，穿透 + 追踪      |
| 地刺   | 生命 | 荆棘领域 | 5 片，毒池扩大 50%     |

**极限突破**。满级武器可以无限叠层，每层 +8% 伤害。这样即使全部内容都满了，选项池也永远不为空。

另外加了**重掷**，每局 3 次，不满意可以重摇三张卡。

原来那个「池子空了塞三个加血」的兜底逻辑删掉了，改成：血量低于 45% 时，用一张治疗替掉第三张卡。有代价，不是白送。

## 02:00 · 小怪建模重做

用户反馈：「小怪建模看不懂，现在只是一小团变成一大团，只有精英怪有精细建模」。

### 问题定位

原实现里 4 种小怪都是单块多面体：

| 类型  | 几何    | 辨识手段 |
| --- | ----- | ---- |
| 墨渍虫 | 二十面体  | 紫色   |
| 尖刺兽 | 八面体   | 青色   |
| 肥球  | 大二十面体 | 黄色   |
| 投掷手 | 六棱锥   | 红色   |

只有颜色和大小两个维度，等于没有造型。

另一个原因：**尺寸太小**。相机高度 25.5、视野角 46°，垂直可见 21.6 个世界单位。小怪高约 1.1 单位，占屏幕高度 5%，在 1080p 下只有 54 像素，看不清任何细节。

### 解法

**第一层：多部件拼装**

写了一个合并函数 `mergeParts`，把多个基础几何按位移、旋转、缩放拼成一个几何，同时给每个部件写入顶点颜色。这样造型可以复杂，但渲染成本不变——仍然是一个 `InstancedMesh`，一个小怪 1 个 draw call。

顶点色的价值：一个材质能画出身体、眼睛、牙齿、刺的不同颜色，不需要多材质多 pass。

四种怪的新造型：

| 类型  | 部件构成                                    |
| --- | --------------------------------------- |
| 墨渍虫 | 压扁球体 + 两只白眼球 + 两个黑瞳 + 三根洋红触须            |
| 尖刺兽 | 八面体 + 五根黄刺（顶部一根、四向斜出）+ 一道黑色横眼           |
| 肥球  | 大球体 + 黑色裂口 + 三颗白牙 + 两只红眼 + 两条紫短腿        |
| 投掷手 | 柱状身体 + 圆头 + 白眼球 + 高举的黄色弹药 + 深红手臂 + 紫色尖帽 |

**第二层：放大**

渲染缩放 1.20~1.25 倍，同时把碰撞半径同步上调（0.62→0.70 等），避免出现「打不到」或「隔着空气被打」。

**第三层：身份区分**

玩家和怪物混在一起时找不到自己，所以给玩家脚底加了一个双层光环：内圈青色慢转，外圈洋红反向快转。精英怪保留黄色光环，半径从 `r×2.05` 提到 `r×2.7`，并把透明度从 0.8 降到 0.55，避免盖住精英本体。

### 顺带修的相机

相机高度 25.5 → 24，让角色在画面里更大一点。

## 02:35 · 修相机抖动（严重 bug）

用户反馈：按 WASD 移动时画面跟着抖，往前按画面会往前甩一下。

### 根因

问题出在 02:00 加进去的相机前瞻。

```js
// 出问题的写法
var lookX = px + (hero.mx||0)*1.9;
var lookZ = pz + (hero.mz||0)*1.9;
camera.position.lerp(_camWant, ...);   // 位置：平滑插值
camera.lookAt(lookX, 0.6, lookZ - 4);  // 视线：直接用突变值
```

`hero.mx/mz` 是输入方向，不是速度。键盘输入是离散的，按下瞬间从 0 跳到 1，松开从 1 跳回 0。

所以每次按键和松键，`lookAt` 的目标点瞬间移动 1.9 个单位，而相机位置还在慢慢追。视线转了，镜头没跟上，画面就甩一下。按一次抖两次（按下一次、松开一次）。

### 修法

两条改动：

**第一，前瞻偏移自己平滑。** 维护一个 `camOffX/camOffZ`，每帧朝目标值逼近，时间常数 0.32 秒。

```js
var k = 1 - Math.exp(-dt / (CAM_LEAD / 3));
camOffX += (tOffX - camOffX) * k;
```

**第二，视线角度写死。** 相机只平移，不转动：

```js
camera.lookAt(camera.position.x, 0.6, camera.position.z - camZ - 5);
```

视线方向永远是 `(0, 0.6-camH, -(camZ+5))`，和玩家位置、输入状态都无关。这样画面在数学上不可能因为输入变化而旋转。

「跟手」的效果由前瞻偏移表达，镜头本身保持绝对稳定。

### 验证

用无头浏览器按住 W 键 800 毫秒，每帧采样相机和玩家的世界坐标：

| 指标      | 结果                                                     |
| ------- | ------------------------------------------------------ |
| 相机 z 序列 | 16.50 → 16.20 → 15.75 → 15.53 → 15.01 → … → 10.01，单调递减 |
| 帧间位移符号  | 全程与玩家移动方向一致，无反向                                        |
| 松开按键后   | 相机平滑减速到静止，无回弹                                          |

修复前，松键那一帧会出现「相机往后退」的情况，那就是甩动的来源。现在没有了。

## 02:42 · 相机抽搐，第二次修（第一次没修好）

02:35 那次修完，用户反馈「还是抽搐，你第一版是不抽搐的」。

### 第一次为什么没修好

02:35 的判断是「lookAt 直接吃了未平滑的输入值」，所以做了两件事：给前瞻偏移加平滑、把视线角度写死。

第一件事是对的，第二件事把问题弄得更糟。

因为把视线改成「盯相机自身前方固定点」之后，相机就不再看玩家了。而相机位置仍然用 `lerp` 插值跟随，玩家加速时相机会落后 1 个多单位。相机落后 + 视线不盯玩家 = 玩家在屏幕上会前后滑。

实测数据：相机相对玩家的 Z 偏移在 16.5 到 17.77 之间波动，跨度 1.27 个单位。这就是抽搐。

### 真正的根因

两个问题叠加：

1. **前瞻偏移**：玩家停下时相机要往回飘 1.6 个单位。玩家不动，画面在动。
2. **位置插值**：`lerp` 让相机滞后，玩家加速时落后、减速时追上。

第一版这两个都没有：相机不做前瞻，位置插值用的是 `lerp` 但视线始终盯玩家，所以滞后不会体现为画面滑动。

### 修法：硬跟随

去掉前瞻，去掉插值，相机位置直接算：

```js
camera.position.set(px + sx, camH + sy, pz + camZ + sz);
camera.lookAt(px + sx*0.5, 0.6, pz - 4);
```

玩家在屏幕上的位置由这个公式唯一确定，不随时间变化。

### 验证：直接测玩家在屏幕上的像素坐标

之前的验证方法不对。我测的是「相机相对玩家的偏移」，这个值本来就该有变化（玩家在动）。真正该测的是「玩家投影到屏幕的像素坐标」，这个值必须恒定。

按住 W 点按四次加长按 D 一次，共 126 帧采样：

| 指标        | 结果               |
| --------- | ---------------- |
| 玩家屏幕 X 坐标 | 640.000，126 帧无变化 |
| 玩家屏幕 Y 坐标 | 491.820，126 帧无变化 |
| 帧间最大跳变    | 0.0000 像素        |

玩家在屏幕上完全不动，只有世界在滚动。

### 教训

「跟手」和「稳定」在相机上是矛盾的。割草游戏里稳定优先，任何让相机相对玩家产生位移的设计都会变成抽搐。这个功能不该加。

## 02:50 · 背景音乐

用户要求：开源或免费商用的背景音乐，或者直接用 8-bit / 16-bit 风格谱写一段，循环播放。菜单舒缓，进游戏时有一个「咻」的切换音效，然后放动感版本。

### 为什么不用外部音频文件

考虑过三条路：

| 方案                       | 问题                                              |
| ------------------------ | ----------------------------------------------- |
| 找 CC0 素材站的芯片音乐           | 单文件 HTML 会变成「HTML + mp3」，破坏零外部依赖。而且循环点难对齐，接缝会听到 |
| 用 Free Music Archive 的曲子 | 参赛作品审核会问素材来源，虽然可商用但不如完全原创干净                     |
| Web Audio 现场合成           | 没有这些问题                                          |

选了第三条。三个好处：波形是自己算的，零版权风险；不占文件体积；音符按网格排，循环天然无缝。

### 曲式

四小节一循环，和弦走 Am - F - C - G，这是最通用的流行进行，听感不腻。

```
| Am  | F   | C   | G   |
  A小调 F大调 C大调 G大调
```

两个模式共用同一套和声，切模式只换配器和速度：

|      | 菜单（calm）        | 战斗（battle）     |
| ---- | --------------- | -------------- |
| 速度   | 84 BPM          | 132 BPM        |
| 低音   | 每拍根音            | 每拍根音           |
| 分解和弦 | 八分音符            | 十六分音符          |
| 铺底长音 | 有，音量大           | 有，音量小          |
| 主旋律  | 无               | 有              |
| 鼓    | 只有每半小节一下轻 hihat | 底鼓 + 军鼓 + 踩镲全套 |

### 实现要点

**调度用系统时钟，不用帧时钟。** 如果每帧检查「该不该响下一个音」，帧率波动会让节奏不稳。标准做法是提前 120 毫秒把未来要响的音排进队列，每 25 毫秒补一次。这样即使掉帧，节拍也是准的。

```js
while(nextTime < AC.currentTime + 0.12){
  // 排这个 16 分音符上所有该响的声部
  nextTime += stepDur;
}
```

**音色全部是基础波形。** 方波做分解和旋律（芯片音乐的味道就在方波的谐波里），三角波做低音和铺底（比方波柔，不刺耳），正弦波做底鼓（扫频），白噪声过高通做军鼓和踩镲。

**循环的实现方式**：一个 64 步的计数器，走到 63 回 0。因为第 5 小节和第 1 小节的和弦相同，所以循环处听不出接缝。

### 「咻」的音效

进游戏时播的过场音，两层叠加：

1. 白噪声过带通滤波器，中心频率从 420Hz 扫到 5200Hz 再落回 880Hz，音量包络前重后轻。
2. 一条正弦波从 300Hz 上滑到 2450Hz，短促，音量低。

两层同步触发，听感就是「咻」的一下。

### 浏览器自动播放限制

浏览器不允许页面加载后自动出声，必须等用户手势。所以音乐在第一次点击或按键时才启动。

标题页底部加了一行提示「点击任意处开启背景音乐」。

### 验证方式

耳听不了（无头浏览器没有声卡），所以测电平。给 BGM 的输出节点接一个分析器，每帧算 RMS：

| 模式        | 峰值   | RMS 特征     |
| --------- | ---- | ---------- |
| 菜单 calm   | 0.24 | 有起伏，音符间有间隙 |
| 战斗 battle | 0.41 | 更连续，密度明显更高 |

两个模式的数据差异符合设计预期（舒缓 = 稀疏，动感 = 密集）。

### 音量平衡

BGM 走独立通道直连输出，音效走原来的通道。第一版 BGM 峰值 0.8、音效 0.32，BGM 会盖掉射击和击杀音。调整后 BGM 降到 0.42、音效提到 0.5，现在音效听得清，音乐在后面垫着。

### 开关

左下角按钮，或者 M 键。开关是 0.28 秒淡入淡出，不硬切。

### 暂停联动

之前的 `togglePause` 只改了游戏状态，没管音乐。

现在暂停时调用 `BGM.pause()`：清掉调度器的定时器，输出音量淡出 0.22 秒。恢复时 `BGM.resume()`：从当前位置重新排音，淡入 0.35 秒。

不是把音量降到 0 继续排音，而是真的停掉调度器。原因是暂停可能持续很久，空转浪费 CPU，而且恢复时如果继续在原来的时间轴上排音，会一次性补上几十个音符，听起来像跳帧。

背包（TAB）打开时也做同样处理，因为那也是暂停状态。放弃本局（quitbtn）时先恢复音乐再结算，结算界面要放舒缓版。

## 03:15 竖屏判断重做 + 进游戏自动锁横屏

用户反馈：手机已经横过来了，遮罩还挂着。

### 根因：不是判断错，是判断得太早

原来的写法：

```js
addEventListener('orientationchange', function(){ setTimeout(checkOrient, 220); });
```

`orientationchange` 事件在部分安卓浏览器上触发时，`window.innerWidth/innerHeight` **还没更新**。实测延迟能到 600-800ms（跟具体机型和浏览器版本有关）。我只等了 220ms，读到的还是转屏前的旧尺寸，于是判定为竖屏，遮罩亮起。

之后没有新事件再触发检查，遮罩就永远挂在那里。这就是「我明明横屏了」。

### 为什么不用陀螺仪

陀螺仪（DeviceOrientationEvent）读到的是**设备物理姿态**，不是屏幕方向。三个问题：

1. iOS 13 起要单独申请权限，会多弹一个授权框
2. 躺着玩时手机平面朝上，beta 接近 0，判断不出横竖
3. 设备姿态和屏幕方向是两件事：系统允许在物理横握时把界面锁成竖屏

真正对应「屏幕朝哪」的 API 是 `screen.orientation.type`，它直接给出 `portrait-primary` / `landscape-primary` 这类值。这是系统层面的答案，比自己推算准，也不需要授权。

### 改法：三层依据 + 多段重试 + 主动锁屏

**第一层，判断依据按权威度排序**

```js
function isPortraitNow(){
  var so = window.screen && window.screen.orientation;
  if(so && so.type) return so.type.indexOf('portrait') === 0;   // 系统直给
  return window.innerHeight > window.innerWidth * 1.34;          // 旧浏览器兜底
}
```

兜底分支用了 **1.34 倍阈值**，只有高度明显大于宽度才算竖屏。因为手机浏览器的地址栏、桌面窄窗口都会让高比宽大一点点，按原来 `h > w` 的等比判断会误触。

**第二层，触屏判断收紧**

```js
function isTouchDevice(){
  if(navigator.maxTouchPoints <= 0) return false;
  if(window.matchMedia){
    if(window.matchMedia('(hover: none)').matches) return true;   // 手机平板，没有悬停
    if(window.matchMedia('(pointer: coarse)').matches) return true;
    return false;                                                 // 桌面，含触屏笔记本
  }
  return 'ontouchstart' in window;
}
```

加了 `hover: none` 这一条。桌面触屏笔记本虽然有 touch 点数，但主指针能悬停，所以判为桌面。**电脑上再也不会弹这个遮罩**。

**第三层，转屏检查改成 4 段重试**

```js
orientTimers = [60, 180, 420, 850].map(function(ms){
  return setTimeout(checkOrient, ms);
});
```

转屏后 60ms、180ms、420ms、850ms 各查一次，覆盖不同浏览器的延迟差异。晚到的那次读到正确值，遮罩就撤掉。同时监听 `screen.orientation` 的 change 事件，比 `orientationchange` 更准。

**第四层，进游戏直接请求全屏横屏**


```js
function startGame(){
  unlockAudio();
  tryLockLandscape();   // 用户点击这一下里请求
  ...
}
```

`tryLockLandscape()` 做两件事：`requestFullscreen()`，然后 `screen.orientation.lock('landscape')`。

这个 API 有两个硬约束：**必须由用户手势触发**、**必须在全屏状态下才生效**。所以只能放在点击「开始对战」的那一刻。「进去就直接强制横屏」在这里才成立。

平台差异：

| 平台           | 结果                                   |
| ------------ | ------------------------------------ |
| 安卓 Chrome    | 真正锁死，物理转成竖屏也不变                       |
| iOS Safari   | 不支持 `lock`，锁不住，回落到遮罩                 |
| 桌面           | `isTouchDevice()` 为 false，直接返回，什么都不做 |
| iframe 内（预览） | 全屏请求被拒，catch 掉，不影响游戏                 |

### 遮罩本身也改了：不再挡死

原来只有一个提示，锁不住就卡住。现在两个按钮：

- **自动横屏** → 再请求一次锁屏
- **就这样玩** → 关掉遮罩，竖着也能玩（相机是俯视的，视野窄但不影响操作）

这样任何设备上都不可能被这个遮罩卡住。

### 顺带修的一个漏洞

原来竖屏遮罩出现时只暂停音乐，游戏逻辑还在跑。玩家转个屏回来，血掉了一半。现在遮罩出现时 `S.mode` 一并设为 `pause`，撤掉遮罩时恢复，用 `ORIENT.pausedByRotate` 记录这次暂停是不是遮罩引起的，避免和 ESC 暂停混淆。

### 验证：8 条用例，测的是真代码

没有抄副本，脚本从 `index.html` 里用括号匹配把 `isPortraitNow` / `isTouchDevice` 的函数源码抓出来，注入不同的 `window` / `navigator` 环境执行。

| 场景            | 触屏    | 竖屏    | 结果   |
| ------------- | ----- | ----- | ---- |

| 手机横屏（新 API）   | true  | false | PASS |
| 手机横屏倒转（新 API） | true  | false | PASS |
| 旧 Safari 竖屏   | true  | true  | PASS |

| 桌面窄窗 800×1000 | false | true  | PASS |

**四、背景虚化。** 给 `<body>` 加 `is-title` 类，标题页时对 canvas 施加 `blur(2.5px) brightness(.78)`。3D 场景退成背景，面板成为唯一焦点。`startGame()` 里移除这个类，进入游戏立刻恢复清晰。

这是让「不乱」最有效的一步：文字和卡片的对比度没变，但背景不再跟它们抢注意力。

**五、角色卡加圆形图标。** 两张卡左边各一个 44 像素的圆，里面是名字首字（疾 / 铁），青色和红色区分。有了视觉锚点，选人不用逐字读。

### 改的过程里踩到的三个坑

**坑一：副标题几乎看不见。**

副标题原来继承了 `.sub` 的 `-webkit-text-stroke:3px`。字号只有 12px，描边 3px，等于把字整个涂黑。小字号扛不住大描边——这是网页排版里很常见的一个失误，描边粗细要跟字号成比例。

改成实心标签：黑底 + 黄字 + 2px 黄框，`-webkit-text-stroke:0`。不需要描边了。

**坑二：「铁壁」这张卡的文字是浅灰的。**

白卡没有声明 `color`，继承了 `body` 的浅色文字（原本这是给深色背景设计的）。在白色卡片上就成了浅灰近白，看着像脏的。

修法是显式钉死：`.t-setup{color:var(--ink)}` 和 `.pick{color:var(--ink)}`。**只要背景换了明暗，就必须显式声明文字颜色**，不能靠继承。

**坑三：我误判了一次。**

看缩略截图时以为角色卡被 flex 压缩了，加了 `flex:0 0 auto` 去「修」。再看实际像素才发现卡片高度 82px 本来就是正常的，是缩略图让我看错了。

那次改动本身没错（防止内容溢出时被压扁），但我把「看图得到的结论」当成了事实。教训是：涉及尺寸的问题，要量像素值，不能看缩略图下判断。

## 15:45 数值体检：建表、定位失配、给出修正方案

用户反馈：数值不对，怪的伤害和我的伤害都偏，BOSS 特别菜。

这次没有直接改数字。先建 `docs/爆裂弓箭手_数值分析表.xlsx`（10 张表、212 个公式），把两条曲线摆在一起看。

### 方法：用 TTK 当统一标尺

**TTK = Time To Kill，打死一个目标要几秒。**

不用「血量多少」「DPS 多少」来判断平衡，因为这两个数各自都能编。用 TTK 判断的原因：它是玩家真正感知到的东西，而且能把两条曲线放在同一个坐标系里比。

判定标准：

| TTK        | 体感        |
| ---------- | --------- |
| < 0.1 秒    | 怪是纸，一刀清屏  |
| 0.15-0.3 秒 | 偏脆，割草应该在这 |
| 0.3-0.6 秒  | 合适        |
| > 1 秒      | 打不动，像在打靶  |

### 参考的模型，分三类说清楚

**有文献依据的：**

1. **DPS / TTK 对齐法** —— Ian Schreiber《Game Balance》(CRC Press, 2021) 里对战斗时长的建模思路：先定「这场战斗要打多久」，再反推血量，而不是先拍一个血量再看他撑几秒。这也是动作游戏里最通用的一条。
2. **成长曲线分类** —— 同书把成长分为线性、多项式、指数、对数四类。核心结论是：**加法成长的系统追不上乘法成长的系统**。玩家的伤害是「武器数 × 等级 × 攻击乘区 × 攻速乘区 × 暴击期望」连乘，指数级；敌人血量如果按加法或低次线性涨，必然在中段被甩开。
3. **锯齿难度曲线** —— Tyler Glaiel《Difficulty Curves》(2013)，以及 Jesse Schell《The Art of Game Design》里关于难度节奏的章节。要点是段内爬升、段落之间回落，避免一路单调上升导致后段失去张力。

**行业经验值（不是文献，是通行区间）：**

- 小怪 0.15-0.6 秒、精英 2-4 秒、BOSS 10-60 秒。割草类偏快端，魂类偏慢端。

**我自己推的值（必须标明）：**

- 成长率 R = 1.62、清怪系数、所有「建议值」列的具体数字。这些是按上面三条方法算出来的，不是抄来的。

### 七个问题，全部有实测数字

### 根因只有一个：两条曲线一个是线性一个是指数

```
玩家 DPS：  13 → 32 → 89 → 132 → 497 → 798 → 903 → 1550 → 2200 → 3368   （×259）
敌人血量：  15 → 17 → 19 → 22 → 24 → 28 → 31 → 35 → 40 → 45              （×3）
```

第 4 波左右两条线交叉，之后再无交集。玩家每波变强 30-70%，敌人每波只厚 13%。所以：

- 前 2 波：玩家还没成型，敌人相对厚 → 打不动（问题 3）
- 第 5 波后：玩家成型，敌人还是那么厚 → 秒杀（问题 2）
- BOSS 用的是写死的常数，跟这条曲线完全脱钩 → 最脆（问题 1）

玩家的 ×259 来自乘法叠加：4 把武器 × 每把 5 级 × 攻击 1.8 × 攻速 1.7 × 暴击期望 1.61。只要还允许同时存在四个乘区，这个增长就压不住——**所以不能压玩家，只能让敌人跟上**。

### 修正方案

**P0（必须一起改，三条联动）**

| BOSS 血量 | 820 + (波-1)×120 | 建议DPS × 目标秒数（派生）     |
| 小怪伤害    | base 10         | base 14              |

等下，第 2 波 1.5 倍偏差还是偏肉。这是曲线形状问题，但至少不再是 15 倍的断崖。第 2 波偏肉其实是好事：让玩家在第一波末尾到第二波之间完成第一次武器升级。

**指数曲线为什么不从头就完美**：玩家 DPS 在第 1-3 波涨了 6.8 倍（13→89），在第 3-5 波涨了 5.6 倍（89→497）。任何单一指数都拟合不了这条折线。真要完全贴合，得让血量倍率也分段。这一步留给实测再调——先解决 15 倍的断崖。

### BOSS 血量为什么要用数组


### Bug ①：宝箱自动塞武器

`openChest()` 里有这么一段：

```js
if(freeNew.length > 0 && hero.weapons.length < 4){
  var nid = pick(freeNew);
  hero.weapons.push({id:nid, lv:1, cd:0, tick:0});   // ← 没选就装上了

```

玩家在打怪，一个 toast 闪过，武器已经在背包里了。

**调研了两个参考游戏，结论完全一致：**

| 游戏                | 做法                                                                                                                                                            |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 弓箭手大作战 / Arrow.io | 所有技能和武器**只有一个来源**：升级时三选一。没有宝箱给武器                                                                                                                              |
| Vampire Survivors | 官方 Wiki 原文：chests will contain a random weapon or passive item **the player currently has**, leveling up the item by one。攻略站的转述更直白：「这游戏的宝箱只会帮您升级**现有**的武器或被动」 |

**行业里没有「宝箱塞新武器」这种做法。** 因为武器是构筑决策，决策必须由玩家做。

改法：宝箱只升级已有武器；全满级时转成极限突破 +1；被动照旧随机。新武器只能从升级三选一的 `wnew` 卡进入。

验证：开 6 个宝箱，弓从 1 级升到 5 级，**武器数量始终是 1，没有新增任何 ID**。

### Bug ②：肥球的「隐形」

结论是**它没隐形，是看不出是怪**。查到三个叠加原因：

**一、脸全在球体下半部，被自己挡住。**

相机的俯角约 55°，看到的是球体的前上方。而裂口放在 `y=0.72, z=0.80`、眼睛在 `y=1.02, z=0.62`。球心在 `y=0.86`、半径 0.88——这些零件**全在球体内部**，被 z-buffer 吃掉了。

画面上就是一个纯黄色圆盘，玩家认不出是生物。

修法：按球面重新算位置。

```
球心 y=0.86、半径 0.88、y 压扁 0.92
y=1.05 处球面水平半径 = 0.855  → 裂口中心放 z=0.80，前表面 0.98，凸出 0.13
y=1.30 处球面水平半径 = 0.739  → 眼睛 x=±0.30 时 z=0.70，凸出
```

脸整个移到 y=1.05～1.30（球体前上方），俯视能看见。

**二、描边对大物体太细。**

描边是沿法线外扩固定 0.03。对半径 0.32 的投掷手柱子，外扩占 9%，很明显；对半径 0.88 的肥球只占 3.4%，几乎看不见。

修法：`outlineGeo(geo, d.outline || 0.03)`，肥球单独给 0.065。

**三、两个紫色小球在球体内部，只露一点，看起来像「耳朵」。**

它们本来是短腿，放在 `y=0.20`。球体在该高度的半径远大于 0.28，所以腿埋在球里，只在两侧露出一小点紫色——就是用户说的「蓝耳朵」。

修法：移到 `x=±0.42, y=0.10`，完全在球体外，成为真正的脚。

修完的肥球：黄色大球 + 粗黑描边 + 正面两颗红眼（带黑瞳）+ 黑裂口 + 三颗白牙。和墨渍虫、投掷手放在一起，三种怪的识别度都对上了。

### 顺带查出的第三个 bug：刷新权重失控

```js
function waveUnlocks(){
  var w = S.wave, out = ['blob'];
  if(w >= 2) out.push('spiker');
  if(w >= 3) out.push('blob','spiker');   // ← 又来一遍
  ...
}
```

第 3 波把 `blob` 和 `spiker` 又 push 了一次。这个数组是刷新池，元素出现几次就是几份权重。所以第 4 波之后：

| 波次      | 刷新池                                   | blob | spiker | chunk   | thrower |
| ------- | ------------------------------------- | ---- | ------ | ------- | ------- |
| 修正前 W10 | blob/spiker/blob/spiker/chunk/thrower | 2/6  | 2/6    | **1/6** | 1/6     |
| 修正后 W10 | blob/spiker/chunk/thrower/chunk       | 1/5  | 1/5    | **2/5** | 1/5     |

肥球本来就稀，再被压一半，很难遇到——用户觉得「那个怪很奇怪」，一半原因是它太少见。

修法：每波只列一次；第 8 波起给肥球多一份权重（这是唯一允许的加权，对应「肥球成群」的设计意图）。

### 验证：4 条用例

| 用例               | 结果   |
| ---------------- | ---- |
| 开 6 个宝箱后武器数量不变   | PASS |
| 开箱升级了已有武器（弓 1→5） | PASS |
| 开箱只升级已有 ID，不新增   | PASS |
| 第 10 波肥球权重 2/5   | PASS |

4 通过 0 失败。

## 20:05 「隐形怪」定位：尖刺兽被随机旋转翻倒了

用户确认「蓝耳朵黄色身体的怪」是**尖刺兽**（青色八面体 + 五根黄刺）。

内容表起作用了：扫颜色就能对上 ID，不用再靠猜。

### 根因：一行随机旋转

```js
_dm.rotation.set(0, e.ang, 0);
if(key === 'spiker') _dm.rotation.x = e.phase;   // phase = Math.random() * TAU
```

`e.phase` 是 0 到 2π 的随机角，生成时给每只尖刺兽一个 X 轴整圈旋转：

| 随机角  | 结果                  |
| ---- | ------------------- |
| 0°   | 正常站立                |
| 90°  | 横躺，一半身子插进地板         |
| 180° | **完全倒立，整个模型沉到地面以下** |
| 270° | 横躺另一侧               |

约一半的尖刺兽会明显翻倒。翻倒后模型被不透明的地板挡住，而它的贴地阴影是**另一个独立的 instancedMesh**（`pushShadow` 按 `e.x/e.z` 单独画），不受本体旋转影响——所以画面上就剩一个影子在动。

**这就是「怪隐形了，只剩底部阴影」的完整解释。** 不是渲染丢实例（前面测过，存活数和渲染数始终 1:1），是模型自己翻到了地下。

### 修法

```js
if(key === 'spiker') _dm.rotation.x = Math.sin(S.t*6 + e.phase) * 0.14;
```

从「固定随机整圈」改成「小幅摆动」，幅度锁在 ±0.14 弧度（±8°）。保留一点翻滚的动感，物理上不可能翻倒。

验证：摆 5 只尖刺兽成一排截图，全部正常站立，青色身体和黄刺完整。

### 为什么之前没找到

我前面查了两轮都以为是渲染管线的问题（frustumCulled、实例池容量、矩阵更新），因为这些是 InstancedMesh 的常见坑。但实测「存活数 == 渲染数」完全一致，说明实例一个没丢。

**我把「看不见」直接等同于「没渲染」，漏掉了「渲染了但翻到地面以下」这个可能。** 判定依据应该是「画面上有没有」，不是「实例数对不对」。

## 20:40 手机 UI 适配：为什么不能拆两个仓库

用户问：手机 UI 乱套了，能不能做成两个仓库？如果有别的技术手段也行。

### 结论：不能拆，理由很具体

| 拆两个仓库的问题      | 具体后果                                                  |
| ------------- | ----------------------------------------------------- |
| 游戏逻辑是同一份      | 2500 行 JS 里，UI 只占 CSS 那 700 行。拆开等于把逻辑复制两遍，改一个 bug 改两处 |
| 版本会漂移         | 已经踩过「一个对象两处定义」的坑（宝箱、刷新权重、描边参数）。拆仓库是把这个坑放大到整个项目        |
| 参赛只交一个链接      | 两个仓库 = 两个部署地址，评审打开哪个？数据也不通                            |
| 真正的差异在布局，不在功能 | 同一个 DOM、同一套 class，只是尺寸和排列不同。这是 CSS 的活，不是架构的活          |

**正确做法：一套 DOM + 按断点切换布局。** 这也是所有商业游戏的通行做法——同一个 UI 系统，靠锚点和安全区适配不同分辨率。

### 但这次真正的病根是断点选错了

翻了一遍，文件里三个媒体查询**全部用 `max-width`**：

```
@media (max-width: 860px)
@media (max-width: 680px)
@media (max-width: 760px)
```

**这是个横屏游戏，真正的约束是高度，不是宽度。**

| 设备        | 宽度  | 高度      |
| --------- | --- | ------- |
| iPhone 横屏 | 844 | **390** |
| 桌面窄窗口     | 844 | 760     |

宽度完全一样，高度差一倍。用 `max-width` 判断等于把两者混为一谈——手机上套用了桌面窄窗口的规则，然后纵向被压扁。

这就是为什么手机上角色卡名字都没了：卡片高度被压到 20px，内容全裁掉。

### 改法：按高度分断点，减信息量而不是缩尺寸

新增 `@media (max-height: 520px)`，专门处理矮屏：

| 位置     | 桌面             | 手机（矮屏）                        |
| ------ | -------------- | ----------------------------- |
| 标题页    | 左右两栏 + 玩法速览    | 单栏，**玩法速览整块隐藏**               |
| 副标题小标签 | 显示             | 隐藏（390 高里不值那 26px）            |
| 角色卡    | 图标 44px + 两行描述 | 图标 28px + 一行描述                |
| 音频控件   | 左上角竖排，46px     | **右上角横排，32px 单图标**，音量面板收进暂停菜单 |
| 升级卡片   | 图标块 + 五行文字     | 纵向压扁，重掷按钮才不会被挤出屏幕             |
| 相机     | 24 / 16.5      | 按高度比例拉近到约 19 / 13，角色不至于太小     |

核心原则：**矮屏是减内容，不是等比缩小。** 玩法速览在手机上本来也没人会读，直接折叠掉。

### 建立回归机制：`tests/layout.test.mjs`

只是改一次没用，下次加功能还会崩。所以写了多尺寸溢出检测：

```bash

msedge --headless=new --remote-debugging-port=9915 about:blank
node tests/layout.test.mjs
```

覆盖六个尺寸（iPhone/小安卓/大安卓/iPad/两种笔记本），每个尺寸检查四个界面（标题/游戏内/升级/背包），逐个元素比对 `getBoundingClientRect()` 和视口边界。

```
PASS  iPhone 12/13 横屏  844x390  四个界面均无溢出
PASS  小屏安卓 横屏      780x360  四个界面均无溢出
PASS  大屏安卓 横屏      915x412  四个界面均无溢出
PASS  iPad 横屏         1024x768  四个界面均无溢出
PASS  笔记本 1440x900            四个界面均无溢出
PASS  笔记本 1280x720            四个界面均无溢出
```

6 通过 0 失败。

**这个脚本的价值不是这次通过，是下次改 UI 能在 20 秒内知道有没有崩。** 肉眼看六种设备的截图不可靠——我自己就看过一次缩略图误判成「卡片被压缩」。

### 一个容易漏的地方

`max-height: 520px` 也会命中桌面的矮窗口（比如 1440×450）。这是有意的：矮就是矮，跟横向有多宽无关。但如果以后要支持超宽矮屏（如拼接屏 1920×400），需要再加宽度条件。

## 2026-10-24 00:45 · 修「丢炸弹卡脚」

**现象**：用炸弹时屏幕一震，玩家移动会明显顿一下，连爆时更严重。

**先回答这是不是机制**：是。`explode()` 里设了 `S.hitstop = 0.05`，而主循环是：

```js
if(S.hitstop > 0){ S.hitstop -= dt; dt *= 0.22; }
```

这 0.05 秒里**整个游戏时间被压到 22%，包括 `updateHero`**。所以是「世界和你一起慢下来」，玩家的手感被打断了。顿帧本身是对的，错在作用对象。

**修法**：把时间拆成两份。

```js
var worldDt = dt;
if(S.hitstop > 0){ S.hitstop -= dt; worldDt = dt * 0.18; }

updateHero(dt);          // 玩家：真实时间
updateWeapons(dt);       // 开火：真实时间
updateEnemies(worldDt);  // 敌人：被压缩
updateBoss(worldDt);
updateBulletArr(bullets, worldDt);
```

**效果**：顿帧的打击感来自「敌人凝固」，跟玩家的手没关系。现在两头都保住——敌人还在顿，你的脚不再被卡。

**为什么不是干脆去掉顿帧**：爆炸需要重量。去掉之后炸弹就变成纯数值伤害，视觉和手感都空了。只停世界是这类游戏的标准做法。

## 2026-10-24 01:10 · 音乐重做：从循环片段改成曲式引擎

**问题**：原来的 BGM 是四小节无限重复，两个模式（calm / battle）只换配器和速度。听两分钟就腻，因为**没有任何段落变化**。

**改法**：把「曲子」变成数据结构。

```js
var SONG = {
  battle: {
    bpm: 134, bars: 16,
    chords: [[57,60,64],[53,57,60],[48,52,55],[55,59,62]],
    sec:    ['a','a','a','a','b','b','b','b','c','c','c','c','a','a','b','b']
  }
};
var SEC = {
  a: {bass:1, arp:8,  lead:0, pad:1, kick:1, snare:0, hat:2},  // 主歌
  b: {bass:1, arp:8,  lead:1, pad:1, kick:1, snare:1, hat:2},  // 副歌
  c: {bass:2, arp:16, lead:2, pad:1, kick:2, snare:2, hat:1}   // 高潮
};
```

「主歌 / 副歌 / 高潮」的差别只体现在两件事上：**声部数量**和**节奏密度**。主歌只有低音和铺底；副歌加旋律和军鼓；高潮是十六分音符 + 双踩 + 镲。

**三首曲子**：

| 场景   | BPM | 小节 | 结构                    | 调性                       |
| ---- | --- | -- | --------------------- | ------------------------ |
| 菜单   | 82  | 8  | 前奏2 + 主题4 + 收尾2       | Am9 - Fmaj7 - Cmaj7 - G6 |
| 战斗   | 134 | 16 | 主歌4 + 副歌4 + 高潮4 + 回落4 | Am - F - C - G           |
| BOSS | 152 | 16 | 主歌4 + 副歌4 + 高潮6 + 尾奏2 | Dm - Bb - F - C          |

**循环怎么保证接得上**：末尾几小节是减配器的过渡段，接回第一小节的前奏。这是结构上的保证，不是靠淡入淡出掩饰接缝。

**乐器扩充**：

- 低音从三角波改成**锯齿波过低通**，有冲击力
- 旋律用两路相差 7 音分的方波，产生合唱宽度
- 军鼓是噪声 + 一条 210Hz 三角波叠的，比纯噪声有厚度
- 新增开合镲、镲片


**转场**：换曲时 gain 在 0.09 秒压到静音，再 0.53 秒抬起来，配合「咻」声，听起来是转场而不是断掉。

**新增两个转场音效**：
- `whooshUp`：从暂停恢复，噪声带通 560→3400Hz + 正弦 420→1500Hz
- `whooshDown`：进暂停，方向相反，2600→380Hz + 980→300Hz

三个「咻」方向明确：进游戏上扬最明显，暂停下坠，恢复上扬。

**验证**：接 `AnalyserNode` 测输出电平。

| 场景 | 峰值 | RMS |
|---|---|---|
| 菜单 | 0.063 | 0.010 |
| 战斗 | 0.247 | 0.019 |
| BOSS | 0.269 | 0.019 |

三档层次分明，零 JS 错误。

## 2026-10-24 01:05 · 修「主页音乐播到一半戛然而止」

**现象**：菜单音乐循环时，某个位置突然没有声音，然后像"重新开始播第二段"，没有首尾衔接的感觉。

**先排除的**：不是循环逻辑断了。`step = (step + 1) % (bars * 16)` 是对的，`nextTime` 也是连续累加，时间轴上没有断层。

**真因有三层，叠在一起才变成"戛然而止"。**

### 第一层：过渡段把节奏声部清零（主因）

菜单段落表是 `['intro','intro','a','a','b','b','a','outro']`，而配器表是：

```js
intro: {bass:0, arp:0, lead:0, pad:1, kick:0, snare:0, hat:0}
outro: {bass:0, arp:0, lead:0, pad:1, kick:0, snare:0, hat:0}
```

**除了铺底长音，全是 0。**

第 8 小节（outro）+ 第 1、2 小节（intro）= **连续 3 小节、8.8 秒没有任何低音、鼓、分解和弦**。`a` 段有低音和踩镲，到 `outro` 全消失，听感就是"音乐停了"；`intro` 继续空，到第 3 小节 `a` 才回来，所以像"第二段"。

我的错误是把「减配器过渡」理解成「去掉所有节奏声部」。正确的减法是**降低密度，不是移除脉搏**——低频脉冲和踩镲是听众判断"歌还在不在"的锚点。

修：

```js
intro: {bass:1, arp:0, lead:0, pad:1, kick:0, snare:0, hat:2}   // 薄，但有心跳
outro: {bass:1, arp:8, lead:0, pad:1, kick:0, snare:0, hat:2}   // 比主歌少一个底鼓
sec:   ['intro','a','a','b','b','a','b','outro']                // 前奏从 2 小节压到 1 小节
```

并在代码里写下一条硬规则：**任何段落都必须至少有 bass 或 hat 在响。**

### 第二层：低音包络是「砰一下就没了」

```js
gn.gain.linearRampToValueAtTime(v, t + 0.012);
gn.gain.exponentialRampToValueAtTime(0.0008, t + dur);   // 一路衰减到底
```

指数衰减意味着低音只占时长的前 20% 听得见，两个低音之间留 0.07 秒完全空白。听感是"点状的砰砰"，不是持续的低音线。

改成三段包络：

```js
gn.gain.linearRampToValueAtTime(v, t + 0.014);
gn.gain.linearRampToValueAtTime(v * 0.82, t + dur * 0.58);   // 保持段
gn.gain.exponentialRampToValueAtTime(0.0008, t + dur);
```

同时把低音时长从 3.6 步改成 3.9 步（每拍间隔 4 步），接近连奏。

### 第三层：铺底每小节从零起音

`pad` 的起音是 `setValueAtTime(0, t)` 然后 ramp 到峰值，而上一小节的 pad 已经衰减干净。所以**每小节开头有 0.3 秒真空**，表现为周期性"一顿一顿"。

修：
- 从 45% 音量起音（听感上是"接着上一小节"）
- 时长从 15.2 步改成 16.4 步，让相邻两个 pad 有重叠
- 起音量从 0.075 提到 0.095

### 顺带修的一个隐患

分解和弦的密度用 `s % (16/arp)` 判断，只支持能整除 16 的密度（8、16）。我给尾奏写 `arp:6` 时会算出 2.67 步，取模判断直接失效，整段分解和弦消失。

改成槽位表映射：

```js
var ARP_SLOTS = { 8: mkSlots([0,2,4,6,8,10,12,14]), 6: mkSlots([0,3,5,8,11,13]) };
```

### 验证方式换了两次，第一次的方法本身是错的

**第一版测量**：接 `AnalyserNode`，`setInterval` 每 50ms 读一次 RMS。测出中位 0.0199，但序列里有孤立极低点（0.003）。

**怀疑**：这些是采样抖动还是真实静音？

**第二版测量**：改用 `ScriptProcessorNode`，它按**音频时钟**回调（每 4096 样本 = 93ms），不受定时器被节流的影响。这个才能测到音乐本身的动态。

**修复前后对比**：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 中位 RMS | 0.0199 | 0.0276 |
| 每秒 RMS 范围 | 有 0.003 的孤立低点 | 0.019 – 0.034，全程平稳 |
| 最长连续低谷 | 多段 | 0.28 秒（且发生在淡入期） |

### 副作用：整体响度涨了 39%，得降回来

内容变饱满之后，同样音量设置下响度提高。用户之前明确说过"音乐盖过音效"，所以默认值从 0.28 降到 0.21（滑杆默认值同步）。

**教训**：改音色的包络会改变整体响度，这不是"只改音质"。任何涉及增益结构的改动，都要重新测混音比例。

## 2026-10-24 01:45 · 配色重构：不是色系接近，是明度没拉开

**用户判断**：「地面上的蓝色经验物与地面底色色系过于接近，难以分辨。」

这个判断对，但根因比「色系接近」更具体。

### 先量化

| 元素 | 颜色 | 明度(L) |
|---|---|---|
| 地板底色 | `#E4F2FD` | 95 |
| 经验球 | `#00E5FF` | 78 |
| 天空/清屏 | `#9ED4F5` | 85 |

经验球比地面**暗 17 档**，而且同属蓝青色系。两件事叠加：灰阶下直接消失，彩色下靠色相勉强能分。

### 调研到的三条原则

| 原则 | 出处要点 | 落到本次 |
|---|---|---|
| **明度对比优先于色相对比** | 「把画面转成灰阶，还能分清才算合格。只靠色相，在运动中和小尺寸下会失效」 | 主指标定为灰阶可辨 |
| **职能色分层** | 金=战利品、红=危险、蓝=友方/交互 | 经验球改金、BOSS 警示用珊瑚红 |
| **环境去饱和** | 「环境的饱和度要比角色低 20-30%，否则前景会被视觉噪声淹没」 | 地面降一档 + 纹路透明度减半 |

### 改动

| 元素 | 旧 | 新 | 理由 |
|---|---|---|---|
| 地板底色 | `#E4F2FD` (L95) | `#C9DFEF` (L82) | 地面占 60% 画面，它越亮前景越难看清 |
| 放射线 | 透明 .42/.85 | .10/.20 | 亮底上的白线是一层噪声 |
| 同心圆 | .55 | .26 | 同上 |
| 网点 | .16 | .10 | 同上 |
| 经验球 | 青 `#00E5FF` | 金 `#FFD24A` + 白核 + 黑壳 | 互补色 + 明度 + 轮廓三重保障 |
| 尖刺兽 | 青 `#00E5FF` | 青蓝 `#12A6C4` | 明度 78→62，与地面拉开 20 |
| 玩家光环内圈 | 青 | 暖白 `#FFF8EE` | 中性色，不与任何敌人撞 |
| 千手墨神八臂 | 青 | 珊瑚红 `#FF4D6D` | 冷背景上的最强暖色 |

### 第一次改完仍然不合格

把经验球改成金色 `#FFC233`（L84），以为和地面 82 有对比。**灰阶截图一看，经验球几乎全消失了**——只差 2 档，等于没差。

这里犯的错是：用「色相不同」代替了「明度不同」。金色和蓝灰在彩色下确实完全不同，但灰阶一压就没了。

### 真正的解法：加黑描边壳

给经验球套一层黑色八面体，`side: THREE.BackSide` + 放大 1.34 倍，形成一圈墨线。

```js
var gemOutPool = instPool(new THREE.OctahedronGeometry(0.30, 0),
  new THREE.MeshBasicMaterial({color:0x0a0a12, side:THREE.BackSide}), 260);
```

黑（L10）和任何明亮背景（L75+）的明度差都在 65 以上，**无论背景换成什么颜色都成立**。这也是美漫的通用解法——所有东西都有墨线。

改完再转灰阶，每个经验球都是「黑边 + 亮心」，全部可辨认。截图存为 `screenshots/16-palette-color.png` 和 `17-palette-gray.png`。

**方法论沉淀**：判断「看不清」时，先不要调色相。把截图转灰阶，如果目标消失了，问题在明度；如果还在但分不清彼此，才是色相问题。这两种病要开的药不一样。

## 2026-10-24 02:20 · BOSS 数值：从「查表」改成「按玩家实时 DPS」

**用户反馈**：第 5 波 BOSS 被瞬间秒杀。

**先算了一下，觉得不对劲**：`hp = EXPECTED_DPS[4] × 16 = 451 × 16 = 7216`。玩家如果按标准配装（DPS 451）打，正好 16 秒。秒杀说明玩家 DPS 远超 451。

但真正的问题不是「血量不够」，而是**血量用了查表值**。`EXPECTED_DPS` 是「典型配装」的期望，写死在代码里，跟玩家实际拿到的牌完全脱节。

### 用四个智能体量化偏差

写了一套多智能体压力测试（见 `docs/TESTING.md`），四个策略各自模拟一种构筑倾向，同一个 7216 血：

| 策略 | 配装 | TTK |
|---|---|---|
| rush | 3 把武器，激光满级 | 42.8 秒 |
| random | 3 把武器，等级低 | 56.8 秒 |
| balanced | 1 把弓 | 90 秒打不完，剩 65% |
| passive | 1 把弓 | 90 秒打不完，剩 61% |

**同一个 BOSS，体验差两到三倍。** 用户遇到「秒杀」是因为他抽到了强配装，而弱配装玩家会觉得 BOSS 打不动。

所以问题不是「血量太少」，是**血量没有跟随玩家强度**。

### 改法

```js
var liveDps = currentBossDPS();          // 开战那一刻读玩家真实 DPS
var targetTtk = kind === 'hands' ? 20 : 12;
var hp = Math.max(260, Math.round(liveDps * targetTtk));
```

`currentBossDPS()` 是新函数，等于 `estimateDPS(true) × 暴击期望`。两个细节：

**1. 新增单目标口径 `estimateDPS(single)`。**

原来的 `estimateDPS()` 乘了「清怪系数」——那个系数是「一发能清几只怪」的折算，镰刀 2.6、地刺 4.6。拿来算单个 BOSS 会把这些 AOE 武器高估两到四倍。血月斩对着一只 BOSS，不会因为它是范围伤害就打出四倍输出。

**2. 补暴击期望。**

`estimateDPS` 算的是基础伤害，没含暴击。打 BOSS 时暴击是实打实的输出：`1 + 暴击率 × (2.0 - 1)`。

**3. 目标秒数不是理论秒数。**

设计 12 秒，不是「DPS 算出来 12 秒就真能 12 秒打完」。实战里玩家要躲冲锋、躲弹幕，有效输出时间约占 60-75%。所以 12 秒对应的是「有效输出 12 秒」，实际墙钟时间会更长。

### 踩到的坑：血量下限

第一版加了 `Math.max(2600, ...)`，理由是「防止 BOSS 变成纸」。

结果：passive 策略（只有一把弓，DPS 约 30）打 2600 血要 **87 秒**。

**下限保护的是 BOSS 的体面，牺牲的是玩家的时间。** 去掉下限后，DPS 30 的玩家面对 360 血的 BOSS，12 秒打完，和其他人体验一致。

### 顺带发现的真实设计缺陷

第 10 波测试里，random 策略（近战/地面武器）90 秒打不完千手墨神，剩 46.8%。

根因：墨神保持 9.5 单位距离 + 会瞬移，镰刀和地刺够不到。

修：**狂暴后（血量过半）保持距离 9.5 → 4.5**。狂暴 = 放弃远程优势开始压制，机制上也更好读——玩家能感觉到「它不躲了」。

### 结果

| 波次 | 样本 | 修复前 | 修复后 | 目标 | 偏差 |
|---|---|---|---|---|---|
| 第 5 波 | 8 | 42 – 90 秒（含打不完） | **6.5 – 16.6 秒** | 12 秒 | 1.08× |
| 第 10 波 | 4 | 16.4 – 90 秒（含超时） | **16.4 – 21.9 秒** | 20 秒 | 0.97× |

方差从 5 倍收敛到 2.6 倍。

### 测试体系本身也修了两个 bug

## 01:40 起播 3 秒没声音：慢淡入 + 中位小节是空的

用户反馈「开头会出现好几秒的 BGM 沉默」。这次先量再改。

### 测量

新写 `tests/audio-start.test.mjs`：用 ScriptProcessorNode 挂在 BGM 输出节点上，
按音频时钟采样（每 93ms 一块），测「点击 → 第一个听得见的采样点」。

第一版结果：

| 指标 | 数值 |
|---|---|
| 首次可听 | **1.07 秒** |
| 第 1 秒平均音量 / 峰值 | **1.4%** |
| 0 – 0.8 秒 | 0.0000 – 0.0004（等于静音） |

前 0.8 秒真的什么都没有，1 秒后才爬到能听出来的程度。

### 三个原因，叠在一起

**一、起播做了 1.4 秒指数淡入。**

```js
step = 0; nextTime = AC.currentTime + 0.1;
this._apply(1.4);      // 从 0.0001 指数爬到 0.21，用时 1.4 秒
```

指数曲线的前半段几乎等于 0：0.2 秒时增益 0.0003，0.7 秒时 0.0046。
**起播时根本没有「上一段音乐」要淡出，这个淡入只是自己在制造沉默。**

**二、预排 0.1 秒。** 第一个音排在 `currentTime + 0.1`，这是实打实的静音。

**三、最先放的小节是全场最薄的。** menu 段落表是
`['intro','a','a','b','b','a','b','outro']`，而 `SEC.intro` 是
`{arp:0, kick:0}` —— 只有低音、四分踩镲、一条很轻的铺底。
把最薄的一小节放在整首的最开头。

### 改法

| 项 | 之前 | 现在 |
|---|---|---|
| 起播增益 | 1.4 秒指数淡入 | 直接 62%，0.22 秒补满 |
| 预排 | 100ms | 60ms |
| intro 配器 | arp:0 / kick:0 / crash:0 | arp:8 / kick:1 / **crash:1**（第一拍有镲片） |
| 换曲时若刚起播 | 仍走「压下 0.09s + 抬起 0.62s」 | 跳过压下，0.25 秒补满 |

最后一条是查路径时想到的：玩家第一次交互如果就是点「开始对战」，
菜单曲刚起 0.1 秒就被切走，那道「先压下」等于把刚出来的声音又抹掉。
现在 `setMode` 会看 `currentTime - startedAt < 0.35` 判断有没有旧曲子可淡出。

### 顺带修小节线前的塌陷

测完起播看波形，发现每小节最后一两成时长会掉到峰值的 5%。
原因是低音包络收到 `0.0008` 才停 —— **每个音的尾巴都是听不见的**，
一拍接一拍就是「顿、顿、顿」。改成收到 26%，下一拍直接接上。

铺底同理：释放目标从 `0.0006` 改到 `pk * 0.12`，
让相邻两小节真正重叠，而不是每小节先塌一下再起来。

### 结果

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 首次可听 | 1.07 秒 | **0 秒** |
| 第 1 秒 / 峰值 | 1.4% | **62%** |
| 稳态段最长低谷 | 多段（0.25 秒级，小节线附近） | **0 秒** |
| 循环点最低 / 中位 | — | 0.0124 / 0.029（46%，合格线 30%） |

26 秒每秒音量：`0.034 0.029 0.028 0.032 0.029 0.024 0.035 … 0.028 0.032 0.035 0.030`
—— 一条平线，起播和循环点都听不出接缝。

另外单独验了「首次点击 = 开始对战」这条路径：模式切到 battle，
首听 0 秒，峰值 0.058，前 3 秒无空档，零 JS 错误。

### 这个测试留着

`tests/audio-start.test.mjs` 现在是长期的音频回归用例，四条断言：
起播 ≤ 0.35 秒、第 1 秒 ≥ 峰值 35%、最长低谷 ≤ 0.5 秒、循环点 ≥ 中位 30%。
改任何音色或包络都可以先跑它，20 秒出结论。

**踩坑记录**：写这个测试时把 Node 侧的常量 `CAPTURE_SEC` 直接写进了
浏览器表达式里，报 `ReferenceError`，而错误信息被我的 `ev()` 吞成了
「EXC:Uncaught」三个字，白查了一轮。后来把 `exception.description` 打出来才看到。
**调试工具本身报错信息不全，比没有工具更浪费时间。**

## 02:20 v0.10 构筑系统全量改造

这一轮改了 5 个系统，全部按「先量、再改、再量」走。

### 1. 流派：从「六个全局乘区」到「三条线」

原来的 6 个被动（攻击 / 攻速 / 暴击 / 移速 / 生命 / 拾取）对 6 把武器收益完全相同，
所以最优策略就是「来什么点什么」。这不是卡池随机的问题，是系统没给取舍。

改成：

| 线 | 武器 | 精通每级 | 副属性 |
|---|---|---|---|
| 贴身 | 环绕镰 / 地刺 | 本线伤害 +20% | 范围 +6%/级 |
| 投掷 | 炸弹 / 回旋镖 | 本线伤害 +20% | 暴击 +4%/级 |
| 射击 | 爆裂弓 / 激光 | 本线伤害 +20% | 攻速 +5%/级 |

- 3 张通用卡（移速 / 生命 / 拾取）不加伤害
- **同线双持 → 该线伤害 ×1.30**（每线只有 2 把武器，这是「专精」的回报）
- 超武前置从「任意被动 3 级」改成「对应流派 3 级」
- 卡池加权：已有武器 ×2.0，匹配流派 ×1.8，不匹配的流派卡 ×0.45
- 两个角色起手不同：疾风 = 弓 + 射击 1 级；铁壁 = 镰刀 + 贴身 1 级

验证（`tests/arch.test.mjs` 7 条全过）：起手分流、套装 ×1.56（1.2×1.3）、
卡池会出流派卡、流派 3 级才出超武卡、2 级不出。

### 2. 超武必杀 + 蓄力环

六个超武各加一个周期技，蓄满按空格放（手机点蓄力环）：

| 超武 | 必杀 | 周期 | 形态 |
|---|---|---|---|
| 箭雨 | 暴雨模式 | 7 秒 | 1.8 秒内攻速 ×1.8、弹数 +2 |
| 湮灭射线 | 过载贯穿 | 6.5 秒 | 4 倍宽光柱贯穿，0.55 秒内每 0.1 秒结算 |
| 血月斩 | 血月 | 6 秒 | 9 单位吸怪 0.35 秒，再 4 倍斩击 + 回血 |
| 陨石雨 | 空袭 | 7 秒 | 12 小 + 1 大，落点圈预告 0.45 秒 |
| 无限回旋 | 超旋 | 5.5 秒 | 1.5 秒内弹数 ×2、速度 ×1.8、穿透无限 |
| 荆棘领域 | 荆棘爆发 | 5 秒 | 环形 16 枚地刺 |

第一版数值太猛：超武必杀让「射击典型」配装 11 秒打穿第 5 波 BOSS。
已把暴雨模式从「攻速 2.6 + 弹 4」降到「1.8 + 2」，贯穿每 tick 从 0.95 降到 0.6。

### 3. 震屏：max → trauma

`shake()` 从 `Math.max` 改成 `Math.min(1, camShake + amt)`，位移 = trauma²，线性衰减。
4 颗炸弹错时爆炸从「4 次独立抽动」变成「一次连贯强震」。

### 4. 远程怪可读性

- 投掷手加 0.45 秒抬手：地面洋红圈从 2.8 收到 1.1，收满才开枪
- 敌弹改四层：黑壳（BackSide）/ 洋红本体 / 粉白内核 / 两段拖尾，全部 depthTest:false 画在最上层
- 敌人开火换低频 `SFX.eshoot()`，不再和玩家的高频枪声共用
- 玩家弹从洋红改成青绿，把洋红整条让给「威胁」

### 5. BOSS 32 / 45 秒

第一版用「估算 DPS × 窗口」，实测误差极大：同一套配装测出 373 到 1211 DPS，
因为扇形武器的命中率随距离和目标移动剧烈变化。

改成**开战 3.5 秒后按真实输出重新校准血量**：

```
先按估算配血 → 打 3.5 秒 → 量真实 DPS → maxhp = 真实DPS × 目标窗口 → 血条重置为满
```

验证（`tests/boss-ttk.test.mjs`，真实游戏时间计时）：
第 5 波「射击典型」实测 **34.08 秒 / 目标 32 秒（1.07×）**。

### 6. 顺手挖出的两个真 bug

**穿透弹在 BOSS 体内逐帧结算**。`updateBulletArr` 里 BOSS 分支没有「已命中」标记，
穿透弹停在 BOSS 体内时每帧都掉血。实测单把五级弓打出 1211 DPS，理论只有 213 ——
**这才是「BOSS 被秒杀」的真正原因**，跟血量公式无关。加了 `b.bossHit` 标记后回到 484。

**没初始化音频时切音乐会崩**。`BGM.setMode` 里 `nextTime = AC.currentTime` 写在判空之前，
浏览器拦截自动播放时结算会抛异常，直接把 gameOver 打断、结算界面出不来。

### 7. 测试本身的三个坑

- 用墙钟计时：软渲染 + dt 上限 0.05 → 游戏时间比墙钟慢 3-5 倍，四个策略集体「超时」
- 4 个浏览器并行：CPU 打满，帧率塌到个位数，一轮十几分钟。改成 2 个一批
- 智能体按卡片文字分类：流派卡文案变成「流派精通 · 贴身线」后全部落进 other，
  智能体永远不点流派卡。改成优先用 class（`archc` / `newc` / `evoc`）

# 2026-10-25 02:20 · 修「炸弹越丢越晃」

## 反馈

> 「这个炸弹太抖了。他一开始还不是很抖，后面丢炸弹丢得越多，屏幕越来越晃。」

## 根因：震屏是纯线性累加，而后期事件密度翻了五倍

`shake()` 原来是 `camShake = Math.min(1, camShake + amt)`，衰减 1.35/秒。问题在于震屏有两个**高频**来源：

| 来源 | 单次强度 | 后期频率 |
|---|---|---|
| 炸弹爆炸 | 0.22 / 颗 | Lv5 一次四颗，cd 1.02 秒 |
| 小怪死亡 | 0.055 / 只 | 炸弹清屏一次死十几只 |

一轮齐射就是 4×0.22 + 15×0.055 ≈ 1.7，衰减只有 1.35/秒 —— **投入永远大于衰减，trauma 被顶到 1 并长期贴顶**。所以前期单颗炸弹（0.22）很舒服，后期变成持续地震。

## 改法：同一批事件边际递减

```js
var shakeWinT = -9, shakeWinAmt = 0;
function shake(amt){
  var t = S.t || 0;
  if(t - shakeWinT > 0.12){ shakeWinT = t; shakeWinAmt = 0; }   // 0.12 秒算同一批
  var scale = Math.pow(0.75, shakeWinAmt / 0.30);               // 批内第 2、3、4 次递减
  var use = amt * scale;
  shakeWinAmt += amt;
  camShake = Math.min(1, camShake + use * (1 - camShake * 0.25));  // 软饱和
}
```

外加衰减 1.35 → 1.50/秒。**单次事件永远是全额**，所以 BOSS 技能、超武、受击、单颗炸弹的手感一点没动，只有「同一瞬间的第 N 次」被压缩。

## 量化验证（对比相机位移，玩家静止，位移全部来自震屏）

用 `git show HEAD:index.html` 取了修改前的版本做对照，同一场景各跑一遍：

| 场景 | 指标 | 修改前 | 修改后 |
|---|---|---|---|
| 后期密集战斗 | 平均位移 | 0.311 | **0.068（-78%）** |
| | 峰值 | 1.58 | **0.50** |
| | 强震时间占比 | 17% | **0%** |
| 前期单颗炸弹 | 峰值 | 0.048 | 0.039 |

密集战斗从「一直晃」变成「炸一下、随即回稳」；前期单发震感基本不变（0.048 → 0.039，差值是 33ms 采样没对准峰值）。

## 参数调过一轮

第一版用 0.55 的幂 + 0.22 的尺度，实测平均只剩 0.029 —— 压过头了，打击感会丢。放到 0.75 / 0.30 才落在「有冲击但不累积」的位置。记录一下：**这类手感参数不能一次定死，必须拿旧版做对照量。**
